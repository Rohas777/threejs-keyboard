# Общий WebGL-канвас с drei `View`

Статус: **запланировано**, не реализовано. Документ описывает переход от нескольких независимых `<Canvas>` к одному общему канвасу, в котором каждая 3D-сцена рисуется в своей области через [`View`](https://drei.docs.pmnd.rs/portals/view) из `@react-three/drei`.

## 1. Зачем

### Как устроено сейчас

На странице шесть независимых `<Canvas>` из `@react-three/fiber`, у каждого свой WebGL-контекст:

| Секция       | Файл                                  | Канвасов | Сцена                                                             |
| ------------ | ------------------------------------- | -------- | ----------------------------------------------------------------- |
| Hero         | `src/sections/Hero/index.tsx`         | 1        | `Hero/Scene.tsx`: клавиатура, 10 кейкапов, HDR, spotLight с тенью |
| Switches     | `src/sections/Switches/index.tsx`     | 4        | `Stage` + `Switch`, контактная тень                               |
| ColorChanger | `src/sections/ColorChanger/index.tsx` | 1        | `ColorChanger/Scene.tsx`: `Stage` + клавиатура, `JumpShadow`      |

Чтобы это было терпимо по производительности, уже сделано следующее:

- Канвасы ниже первого экрана монтируются лениво (`src/hooks/useCanvasVisibility.ts`), а вне вьюпорта переводятся во `frameloop="never"`.
- После интро канвасы по одному прогреваются в простое (`src/lib/warmUp.ts`, `src/hooks/useWarmUp.ts`, `src/components/three/SceneWarmUp.tsx`): `compileAsync`, `initTexture` и один кадр.
- Перемер канваса по скроллу отключён (`src/components/three/canvasDefaults.ts`).

### Что остаётся дорогим при отдельных контекстах

Ресурсы WebGL не разделяются между контекстами, поэтому каждый канвас заново:

1. **Создаёт контекст** и буфер отрисовки (`getContext`, `setSize`).
2. **Компилирует шейдеры.** Программы `MeshStandardMaterial` для Hero и ColorChanger собираются дважды, программы `Stage` — по разу на каждую из пяти сцен.
3. **Загружает геометрию на GPU.** Клавиатура (около 670 тыс. вершин одних только свитчей) живёт в двух контекстах, модель свитча — в четырёх.
4. **Загружает текстуры и генерирует PMREM** для своих HDR-окружений.

Профиль подхода к ColorChanger до прогрева (headless Chrome, SwiftShader, абсолютные значения завышены программным рендером): `getShaderInfoLog` + `getProgramInfoLog` ≈ 24 с, `setSize` ≈ 15 с, `getContext` ≈ 1,7 с, `texSubImage2D` ≈ 0,3 с. Прогрев убрал эту работу из момента скролла, но не из общего бюджета: она по-прежнему выполняется, и GPU-память по-прежнему дублируется.

### Что даёт общий канвас

| Аспект                         | Сейчас (6 контекстов)                     | С `View` (1 контекст)                                                    |
| ------------------------------ | ----------------------------------------- | ------------------------------------------------------------------------ |
| WebGL-контексты                | 6, лимит браузера — около 16              | 1                                                                        |
| Геометрия клавиатуры на GPU    | 2 копии                                   | 1 копия                                                                  |
| Геометрия свитча на GPU        | 4 копии                                   | 1 копия                                                                  |
| Шейдерные программы            | компилируются отдельно в каждом контексте | кэш общий: одинаковые программы компилируются один раз                   |
| Буферы отрисовки               | 6 штук                                    | 1 полноэкранный                                                          |
| Ленивое монтирование и прогрев | нужны                                     | не нужны: всё монтируется сразу, `View` сам пропускает невидимые области |
| Потеря контекста               | ломает одну секцию                        | ломает все 3D-секции (см. «Риски»)                                       |

Ожидаемый эффект: меньше GPU-памяти, нет пиков работы при появлении секций, код проще (уходит инфраструктура ленивого монтирования и прогрева).

## 2. Цели и не-цели

**Цели**

- Один `<Canvas>` на страницу, все 3D-сцены рендерятся через `View`.
- Внешний вид, анимации, события указателя и поддержка `prefers-reduced-motion` такие же, как сейчас.
- Метрики (раздел 8) не хуже текущих, по контекстам и GPU-памяти — заметно лучше.

**Не-цели**

- Менять визуал, модели и ассеты.
- Переходить на `frameloop="demand"`. Это возможный следующий шаг, см. «Открытые вопросы».

## 3. Как работает drei `View` (версия 10.7)

Важные для нас детали поведения, сверенные с `node_modules/@react-three/drei/web/View.js`:

- `View` рендерит DOM-элемент (или следит за `track`-ref) и через `tunnel-rat` отправляет своих детей в `<View.Port />` внутри канваса.
- У каждой `View` своя `THREE.Scene` (`virtualScene`), и она рисуется в общий буфер через scissor/viewport по `getBoundingClientRect()` отслеживаемого элемента. Перед отрисовкой `autoClear` отключается, после восстанавливается.
- Невидимая область (за пределами экрана) не рисуется. Это проверяется на каждом кадре, ручной `frameloop` не нужен.
- Каждая `View` получает свой `compute` для событий. Указатель пересчитывается относительно отслеживаемого элемента, но **только если `event.target === track.current`**. Значит, события указателя должны приходить непосредственно на отслеживаемый элемент, а не на его потомков или элементы поверх него.
- Камера по умолчанию у каждой `View` своя (через `PerspectiveCamera makeDefault` внутри `View`), `Environment` и свет тоже свои — они применяются к сцене этой `View`.

## 4. Целевая архитектура

```
src/app/layout.tsx
└─ <body>
   ├─ Navbar                         z-50
   ├─ <main> секции
   │   ├─ Hero          <View track={heroSceneRef}>      → HeroScene
   │   ├─ Switches ×4   <View track={cardRef}>           → SwitchScene
   │   └─ ColorChanger  <View track={changerRef}>        → ColorChangerScene
   ├─ Footer
   └─ <SharedCanvas/>  position: fixed; inset: 0; pointer-events: none; z-index: 10
        └─ <Canvas eventSource={document.body} eventPrefix="client" …>
             └─ <View.Port />
```

### 4.1. `SharedCanvas`

Новый клиентский компонент `src/components/three/SharedCanvas.tsx`, монтируется в `src/app/layout.tsx` после `{children}`.

```tsx
'use client';

export function SharedCanvas() {
    return (
        <CanvasErrorBoundary onError={handleSharedCanvasError}>
            <Canvas
                {...CANVAS_DEFAULTS}
                shadows="soft"
                eventSource={document.body}
                eventPrefix="client"
                className="pointer-events-none !fixed inset-0 z-10"
            >
                <View.Port />
            </Canvas>
        </CanvasErrorBoundary>
    );
}
```

- `eventSource={document.body}` и `eventPrefix="client"` нужны, потому что канвас сам событий не получает (`pointer-events: none`).
- `document.body` недоступен при SSR, поэтому компонент рендерится только на клиенте: `next/dynamic` с `ssr: false` или флаг «смонтировано» через `useSyncExternalStore`.
- `CANVAS_DEFAULTS` из `src/components/three/canvasDefaults.ts` сохраняется: `dpr: [1, 1.5]`, `resize.scroll: false`. Полноэкранный канвас меняет размер только при ресайзе окна.

### 4.2. Слои и z-index

Канвас лежит **поверх** фонов секций, но **под** их текстом и элементами управления. Нужен аудит слоёв:

| Элемент                                                                                         | Сейчас                      | Нужно                                                                        |
| ----------------------------------------------------------------------------------------------- | --------------------------- | ---------------------------------------------------------------------------- |
| Фоны секций (`blue-gradient-bg` в Hero, градиент ColorChanger, фон карточек свитчей)            | в потоке                    | ниже канваса: без `z-index` или с `z-0`                                      |
| `SharedCanvas`                                                                                  | —                           | `z-10`                                                                       |
| Текст Hero (`.hero-content`), панель выбора в ColorChanger (`Bounded`), кнопки карточек свитчей | в потоке / `z-10`           | выше канваса: `relative z-20`                                                |
| Navbar                                                                                          | `fixed z-50`                | без изменений                                                                |
| Loader                                                                                          | `fixed z-[100]`             | без изменений                                                                |
| Фоновые надписи ColorChanger с `mix-blend-overlay`                                              | `absolute`                  | ниже канваса; проверить, что смешивание идёт с фоном секции, а не с канвасом |
| Белый оверлей Hero (`.hero-scene-fade`)                                                         | под канвасом в sticky-блоке | ниже канваса (`z-0`), иначе он закроет клавиатуру                            |

Затронутые файлы: `Hero/index.tsx`, `Switches/index.tsx`, `ColorChanger/index.tsx`, `globals.css`.

### 4.3. Отслеживаемые элементы и события указателя

Из-за проверки `event.target === track.current` (раздел 3) отслеживаемый элемент должен быть самым верхним элементом под курсором в области сцены:

- **Hero.** События 3D не нужны (сцена с `pointer-events-none`, камера следует за `pointermove` на `window`). Отслеживается sticky-блок `.hero-scene`.
- **Карточки свитчей.** Сейчас под курсором оказывается фоновый `div` с надписями. Нужен отдельный прозрачный элемент `absolute inset-0 z-10` поверх фона и под кнопкой (`z-20`), он и передаётся в `track`. Курсор `pointer` из `Switch.tsx` продолжает работать через `document.body.style.cursor`.
- **ColorChanger.** Отслеживается обёртка канваса (`-mb-[10vh] grow`). Событий в сцене нет.

### 4.4. Сцены

Сцены переносятся внутрь `View` практически без изменений:

```tsx
// Hero/index.tsx
<div ref={heroSceneRef} className="hero-scene … sticky top-0 h-dvh">
    <View track={heroSceneRef} className="absolute inset-0">
        <Scene onReady={…} onIntroComplete={…} />
    </View>
</div>
```

- **Hero.** `PerspectiveCamera makeDefault` и `Environment` уже внутри `Scene`, они станут камерой и окружением этой `View`. `View` передаёт в свой портал `size` по прямоугольнику отслеживаемого элемента. Прямоугольник берётся в момент рендера `CanvasView` и обновляется, когда тот перерисовывается при ресайзе общего канваса. Значит, `scalingFactor` в `Hero/Scene.tsx` (`useThree((s) => s.size.width)`) продолжит считаться по ширине области. Проверить, что при ресайзе окна значение обновляется.
- **Свитчи.** `Stage adjustCamera` использует `Bounds`, а тот читает `size` для подгонки камеры. Внутри `View` это размер области (см. выше). Проверить подгонку на реальной карточке; если она расходится — убрать `adjustCamera` и задать камеру явно, как в ColorChanger.
- **ColorChanger.** `JumpShadow` (`ContactShadows frames={1}`) рендерит тень в свой render target. Внутри `View` render target общий для контекста — проверить, что scissor `View` не обрезает его отрисовку. `ContactShadows` сохраняет и восстанавливает render target сам.
- **Тени.** `shadows="soft"` в общем канвасе включает shadow map для всех сцен. Сейчас тень отбрасывает только spotLight в Hero (`castShadow`), а `Stage` в Switches и ColorChanger идут с контактной тенью или `shadows={false}`. Проверить, что `Stage` не включает `castShadow` у своего spotLight там, где тень не нужна (`shadows={false}` уже так делает), иначе каждая `View` будет рендерить shadow map.

### 4.5. Что удаляется

- `src/hooks/useCanvasVisibility.ts`: `View` сама пропускает невидимые области, а монтирование происходит сразу.
- `src/lib/warmUp.ts`, `src/hooks/useWarmUp.ts`, `src/components/three/SceneWarmUp.tsx` и их тесты. Замена — один прогрев общей сцены после интро, см. 4.6.
- `CanvasErrorBoundary` вокруг отдельных канвасов: остаётся один вокруг `SharedCanvas` (см. «Риски»).
- В `Hero/index.tsx`, `Switches/index.tsx`, `ColorChanger/index.tsx` — условия `wasNear || isWarmUpDue` и пропсы `frameloop`.

### 4.6. Прогрев в общем канвасе

Шейдеры для области компилируются при первом её появлении в кадре. Чтобы не получить пик при подходе к ColorChanger, после интро Hero нужно один раз вызвать `gl.compileAsync` для сцены каждой `View`: сцены доступны через `View`-порталы, например через ref на `group` внутри каждой `View`. Плюс `gl.initTexture` для неактивных наборов кейкапов. Это заменяет текущую очередь прогрева одним вызовом в простое.

### 4.7. Hero и ScrollTrigger

Анимации GSAP и ScrollTrigger работают с объектами three.js и DOM. Смена канваса их не затрагивает. Блокировка и восстановление скролла (`src/lib/scroll.ts`) остаются как есть. Проверить, что фиксированный канвас не мешает расчёту позиций ScrollTrigger: он `position: fixed` и в поток не входит.

## 5. План миграции

Каждый шаг — отдельный коммит, после каждого страница работает.

1. **Подготовка слоёв.** Расставить `z-index` по таблице 4.2 при текущих канвасах. Визуально ничего не меняется.
2. **`SharedCanvas` и Hero.** Добавить `SharedCanvas` в `layout.tsx`, перевести Hero на `View`, удалить его `<Canvas>`. Проверить интро, скролл-волну, восстановление скролла, reduced motion.
3. **ColorChanger.** Перевести на `View`, убрать ленивое монтирование и прогрев для этой секции. Проверить прыжок, тень и смену наборов.
4. **Switches.** Перевести четыре карточки на `View` с отдельным элементом-треком (4.3). Проверить нажатия, звук и курсор.
5. **Прогрев общей сцены (4.6) и удаление старой инфраструктуры (4.5)** вместе с тестами. Обновить README.
6. **Замеры** по разделу 8 и сравнение с текущей веткой.

## 7. Откат

Каждый шаг миграции — отдельный коммит, поэтому откат делается через `git revert` нужных коммитов. До шага 5 старая инфраструктура (ленивое монтирование, прогрев) остаётся в коде для секций, которые ещё не перенесены.

## 8. Критерии приёмки и замеры

Замеры делаются в одинаковых условиях до и после (headless Chrome через CDP, окно 1400×900, `dpr` 1):

| Метрика                                             | Как мерить                                                                           | Ожидание                         |
| --------------------------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------- |
| Число WebGL-контекстов                              | `document.querySelectorAll('canvas').length`                                         | 1                                |
| Draw calls на кадр в Hero / Switches / ColorChanger | счётчик вызовов `drawElements`/`drawArrays` через `addScriptToEvaluateOnNewDocument` | не больше текущих: 205 / 16 / 96 |
| Long tasks при подскролле к ColorChanger            | `PerformanceObserver({ type: 'longtask' })` за окно скролла                          | не больше текущих                |
| Long tasks за первые 15 с загрузки                  | то же, от навигации                                                                  | меньше текущих                   |
| Ресайзы буфера при скролле                          | `MutationObserver` на атрибуты `width`/`height` у `canvas`                           | 0                                |
| GPU-память                                          | `chrome://gpu` / DevTools Memory на реальном GPU                                     | меньше текущей                   |

Функциональная проверка:

- интро Hero, блокировка скролла до его конца;
- перезагрузка со середины страницы: анимации выше позиции в конечном состоянии, скролл разблокирован после лоадера;
- скролл-волна клавиатуры;
- нажатия и звук всех четырёх свитчей, курсор `pointer`;
- смена всех шести наборов кейкапов, тень при прыжке;
- `prefers-reduced-motion: reduce`;
- мобильная ширина (≤ 500 px, масштаб клавиатуры 0,5).

## 9. Открытые вопросы

- Переход на `frameloop="demand"` с `invalidate()` из GSAP-таймлайнов и `useFrame` с анимацией (`Float`, камера Hero). Это даст ноль кадров в простое, но потребует прокинуть `invalidate` во все анимации. Решать после миграции по замерам.
- Нужен ли `View` для BentoBox (сейчас там статичные рендеры)? Пока нет.
